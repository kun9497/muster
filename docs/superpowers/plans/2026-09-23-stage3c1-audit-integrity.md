# Stage 3C-1 — Audit Pipeline Health and Package Integrity Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Ship spec 3C-1 — three new collectors (`audit`, `fim`, `pkgverify`), the `sudo.log.*` and journal-upload / rsyslog-remote extensions, two `services` rows, the `--verify-timeout` / `--no-verify` flags, the deep-based evaluator rule (D30) and nine controls of category `beyond` — so a default `check` says whether a host records what happens to it and whether its packaged files are what the package manager installed, and a `--deep` run verifies the whole package database with fixed arguments.

**Architecture:** Each collector is one `register.go`-style file plus its parsers, declared with exact `Reads` and fixed-argument `Commands`, writing the spec's 64 registry keys through the existing `collect.Builder` seams: two `setting<bool>` audit keys built like 3B's sysctl (effective is a copy of runtime), nine permission leaves per audit path through `writePermFacts`, capped `list<record>` keys with `truncated` on the envelope, and `packages.verify.*` written only when the Builder says `--deep` without `--no-verify` was given and the run is root (the walk's own gate). The evaluator's walk gate becomes a table of deep families. Controls follow 3B's shapes (`applies_when` container gate, mechanisms with a catch-all, `params` lists with `op: in`).

**Tech Stack:** Go 1.25, `gopkg.in/yaml.v3`, the existing `collect.Access` / `Builder` / `writePermFacts` / `mergeDropins` / `chainScan` / `commandFailure` / `fsAccess` seams, the 3F gates (fixture harness, mutation test, fuzz inventory, oracles, examples), GitHub Actions. No new dependency (D28).

**Spec:** `docs/superpowers/specs/2026-09-23-stage3c1-audit-integrity-design.md` (I-1…I-12; §3 facts, §4 controls, §5 D30, §6 environments, §7 tests and documents, §8 parked), committed at `627f198`, with the pre-flight corrections of this plan's commits (J-1…J-6: the `auditctl` exit codes, what a container can and cannot answer, dpkg's exit code and output form, the AIDE facts of the three releases, the directory modes; J-19…J-24 from the two pre-flight reviews of 2026-09-28: the fixture rule for list parameters, the directory clauses of `audit_log_permissions`, an `unsupported` completeness fact, the equivalent mutants, the rules.d probe). - **Ruling J-1 (`auditctl` classification, corrects spec I-3).** `auditctl` gates on the effective `CAP_AUDIT_CONTROL`, not the uid (audit-userspace `audit_can_control()`), and prints `You must be root to run this program.` with exit **4** for a non-root caller and for root in a container without the capability; the kernel refuses `AUDIT_GET`/`AUDIT_LIST_RULES` from any non-init pid namespace with EPERM, which `auditctl` reports as `Error sending status request (Operation not permitted)` / `Error sending rule list data request (Operation not permitted)` and exit **255**; a non-init user namespace gets ECONNREFUSED, which `auditctl -s` swallows (`The audit system is disabled`, exit 0, no `enabled` line). `auditctl -l` as euid 0 skips the capability gate. The runtime reader classifies: exit 4 → `denied` when `euid() != 0`, `unsupported` ("no CAP_AUDIT_CONTROL: an unprivileged container") when root; exit 255 with `Operation not permitted` → `unsupported` ("kernel audit is not reachable from this pid namespace"); exit 0 without an `enabled` line (or stderr `The audit system is disabled`) → `unsupported` ("the kernel gave no audit status"); `audit support not in kernel` / `Cannot open netlink audit socket` → `unsupported`; any other non-zero exit → `error` naming the command and code; the binary absent (`Err` set, exit -1) → `absent` ("auditctl is not installed"). Never `PASS` on a status nobody parsed.

- **Ruling J-3 (dpkg's exit code carries no verdict, corrects spec principle 2).** `dpkg --verify` with no arguments always exits 0 (`verify()` returns `rc` only for a named package that is not installed). `packages.verify.complete` is true when the command exited 0, or exited 1 with at least one parsed row, and the output was not truncated; exit 1 with no parsed row is `error` carrying `stats.stderr_head` (rpm's locked-database case); any other exit is `error`; a kill is `timeout`; a cap is `truncated`. The verdict is always read from the rows.
- **Ruling J-4 (the verify line grammar).** One regexp for both tools: `^(?P<flags>[S.?M5DLUGTP]{9}|missing  )\s{1,3}(?P<type>[a-z ])\s(?P<path>/.*?)(?: \((?P<note>[^)]*)\))?$` — rpm separates the nine columns from the type letter by two spaces, dpkg by one; both print `missing` padded to nine; dpkg fills only column 3 (`5`) and column 2 (`M`, no longer a regular file); rpm's type letters are `c d g l r` plus `a` (artifact) and, rarely, `s m n`; an unknown letter is kept as the letter and never drops the row; a trailing ` (Permission denied)` or ` (not installed)` note is kept in `note`. Attribute names: `size mode digest device link user group mtime caps` for `S M 5 D L U G T P`; a `?` is untested; `missing` rows carry `["missing"]`. A line matching neither form is counted in `stats.lines` and its first three kept in `stats.stderr_head`'s sibling `stats.unparsed_head` (record field, evidence).
